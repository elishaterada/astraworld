# M1 responsiveness revision — protocol 2

Implemented 2026-09-06. M1 only; no gathering, inventory, combat, crafting, taming, building or durable gameplay saving. The user explicitly selected **Vercel only**, superseding the research proposal for a separate long-lived server host. Existing Vercel Redis and WebSockets are reused; no service was provisioned.

The subsequent user-authorized [eight-player expansion](M1_EIGHT_PLAYERS.md) supersedes the original two-member cap. Measurements below describe the original two-player runs unless labeled otherwise.

## Play

Choose a name and Fern, Ember, Iris or Hazel. Enter Meadow requests fullscreen. Menu → Copy invite link admits up to seven friends with their own names and looks. WASD/arrows move; pointing sets facing independently of movement; Space performs a cosmetic wave. Escape/menu releases movement. The wave uses an explicitly provisional text/hand marker, not finished character animation. Eight facing values map to four available sprite directions; remote walk/idle animation now follows replicated state.

## Contract and implementation

- `packages/protocol/realtime.ts`: strict version 2 hello/frames/snapshot schemas. A frame has a monotonically increasing sequence, four movement-key bits, facing 0–7 and optional wave. Run-length encoding batches consecutive identical controls. The server accepts at most 60 frames / 8 KiB, rejects unknown authority fields, conflicting replay and out-of-window sequences. The gateway binds identity and connection generation after authenticating the opaque session credential.
- `packages/simulation/realtime.ts`: pure shared 60 Hz movement and action rules. Server acknowledgements identify the last **consumed contiguous frame**, not the newest received message. Retries are deduplicated; missing frames wait for retransmission. Time credits accrue at 60 per server second, capped at 30, with at most six consumed per tick. Thus jitter can catch up within a bounded half-second allowance, while packet floods cannot grant unbounded extra time. The server controls the wave's one-second simulation cooldown and its generation/sequence identity. Waves confer no shared reward or world mutation.
- `app/network.ts`: 60 Hz prediction is separate from the 20 Hz maximum send loop. Unacknowledged history, including the discrete wave, is resent and coalesced; no trailing debounce. Settled idle clients send a one-second presence heartbeat. Prediction stops after 750 ms without snapshots or 60 pending frames. Reconciliation starts from accepted state and replays only outstanding frames. Small presentation corrections decay over 80 ms; large corrections snap, and collision checks suppress invalid presentation offsets.
- Remote rendering uses a server-tick timeline buffered by 150 ms, holds at the latest position instead of unlimited extrapolation, and stops walking after stale snapshots. This is a fixed initial buffer, not a claim of adaptive jitter tuning.
- `apps/game-server/realtime.ts`: synchronous in-memory room steps run independently of Redis requests. Authenticated gateways fan out bounded input batches through private Redis pub/sub. One owner simulates the world. At most one checkpoint/publication is in flight, targeted at 10 Hz; new state is sampled on the next opportunity rather than building an unbounded queue. Full projections carry position, facing, moving state, look and last accepted action. Nearby projection remains 48 tiles / eight members.
- The Redis Lua commit verifies both the owner lease token and every actor generation **atomically before checkpoint and publication**. A stale owner or replaced connection cannot publish accepted state. New generations restore the committed position and reset input sequence/action state. Pub/sub is not durable; unacknowledged frame replay repairs missing command deliveries. Accepted checkpoints remain temporary Redis state, not durable saves.
- Lease 1.8 seconds, renewal every 400 ms, recovery acquisition retry every 200 ms. Simulation stops on local lease expiry; only successfully committed projections reach clients. Last-local-socket departure releases ownership so another active Vercel invocation can take over. No forced 45-second room rotation. Room cleanup and simultaneous rejoin are serialized.
- Vercel routes `/api/meadow-v2/{session,play,health}` use a 300-second maximum invocation duration. The client opens a replacement socket at 240 seconds, authenticates it, then retires the preceding socket. Backoff and an independent watchdog handle failed handshakes and missing snapshots. These settings accommodate finite invocations, not an assumption of permanent in-memory hosting. See [Vercel WebSockets lifecycle](https://vercel.com/docs/functions/websockets) and [duration configuration](https://vercel.com/docs/functions/configuring-functions/duration).

## Rolling compatibility

Protocol 1 endpoints and server remain for already-open old deployments. Protocol 2 uses `meadow-session-v2-p8-c4` in tab storage, `production:astraworld-m1v2-p8-c4` in Redis and a version-specific preview namespace. Old and new rooms do not mix; refresh and create a new invitation to use the new controls. No durable gameplay data is migrated. `app/network-legacy.ts` is retained solely for protocol 1 regression tests and is not imported into the active UI. Retire v1 after its last supported deployed client expires.

Local launch uses Redis 6380 and `npm run game:realtime` on 3103/3104. Protocol 1 integration tests retain their own disposable ports. Existing historical evidence is preserved rather than overwritten by new test runs.
